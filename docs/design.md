# 설계 설명

## 1. 구간 재구성 방식

신규 활동이 들어오면 기존 활동을 하나씩 보며 세 경우로 나눕니다.

| 경우 | 처리 |
| --- | --- |
| 신규 활동과 겹치지 않음 | 그대로 둔다 |
| 신규 활동보다 먼저 시작함 | 시작 \~ 신규 시작까지를 원래 활동으로 남긴다 |
| 신규 활동보다 늦게 끝남 | 신규 종료 \~ 종료까지를 원래 활동으로 남긴다 |

한 활동이 두 번째와 세 번째 경우에 모두 해당하면(신규 활동이 기존 활동 한가운데 들어오면) 앞뒤 두 조각이 남습니다. 어느 경우에도 해당하지 않으면(신규 활동이 기존 활동을 완전히 덮으면) 그 활동은 사라집니다. 마지막으로 신규 활동을 추가하고 시작 시각 순으로 정렬합니다.

겹치는 구간이 하나도 없으면 아무것도 잘리지 않고 신규 활동만 추가됩니다. 빈 근무표, 근무표 중간의 빈 시간, 기본 근무 밖의 연장근무가 모두 이 경우라 따로 막거나 분기할 필요가 없습니다. 실무 화면에서도 원본이 없는 칸에 넣은 활동은 신규로 등록됐습니다.

이 방식에서는 시작 시각이 같은 활동이 들어와도 별도 분기가 필요 없습니다. 기존 활동이 신규 활동보다 먼저 시작하지 않으므로 앞쪽 조각이 생기지 않고, 뒤쪽 남은 시간만 원래 활동으로 남습니다. 결과적으로 같은 시작 시각의 구간은 항상 하나만 존재합니다.

근무표의 활동 수를 n이라고 하면 한 번 반영할 때 정렬을 포함해 O(n log n)입니다. 하루 근무표의 활동 수는 많아야 수십 개라 성능보다 규칙이 읽히는 쪽을 우선했습니다.

## 2. 반개방 구간 `[시작, 종료)`

종료 시각을 구간에 포함하지 않으면 09:00\~12:00과 12:00\~13:00이 겹치지 않습니다. 이렇게 하면 다음이 단순해집니다.

- 겹침 판단이 `a.start < b.end && b.start < a.end` 한 줄로 끝납니다.
- 구간 길이가 `종료 - 시작`으로 바로 계산됩니다.
- 이어진 근무표에서 앞 구간의 종료와 뒤 구간의 시작이 같은 값이 되어, 빈틈이나 겹침 검사가 쉬워집니다.

## 3. 입력을 바꾸지 않는 이유

`ScheduleEditor.apply`와 `VacationPlanner.apply`는 입력 리스트를 바꾸지 않고 새 리스트를 돌려줍니다. `Activity`도 필드가 모두 final이고 값을 바꾸는 메서드가 없어 생성 후 바뀌지 않습니다.

- 변경 전과 후를 함께 들고 비교하기 쉽습니다. 실무에서도 변경 전 데이터와 변경 후 데이터를 짝지어 어떤 행을 지우고 어떤 행을 넣을지 정했습니다.
- 계산 도중 예외가 나도 원래 근무표가 망가지지 않습니다. DB였다면 트랜잭션 롤백이 맡을 역할을 메모리에서는 불변 객체가 맡습니다.

## 4. 휴가 반영 순서

1. 그날 휴가들의 차감 시간 합계를 구합니다.
2. 합계가 소정근로시간 이상이면 근무 시작부터 종료까지를 휴가 한 건으로 바꾸고 끝냅니다.
3. 아니면 휴가마다 근무시간으로 계산하는 활동만 골라, 오전 휴가는 앞에서부터, 오후 휴가는 뒤에서부터 남은 차감 시간만큼 휴가 구간을 만듭니다.
4. 만든 휴가 구간을 `ScheduleEditor.apply`로 하나씩 반영합니다.

종일 여부를 시간이 이어지는지로 판단하지 않는 이유는, 오전반차와 오후반차 사이에 점심이 끼면 두 휴가가 시간상 떨어져 있기 때문입니다. 실무에서도 이 경우를 합계 기준으로 판정했습니다.

휴가 계산과 구간 분할을 나눠 둔 덕분에, 휴가 쪽은 "어느 시간을 휴가로 만들지"만 계산하고 실제로 자르고 붙이는 일은 이미 검증된 `ScheduleEditor`가 맡습니다.

## 5. 야간 근무와 일시 기준 정렬

구간의 시작과 종료는 시각만이 아니라 날짜를 포함한 일시로 가집니다. 실무에서 철야조 근무표를 시각 문자열로 정렬했을 때 04:00이 18:00보다 앞에 와서 순서가 뒤집히는 문제가 있었고, 날짜를 포함한 일시로 정렬해 해결했습니다. 이 예제도 같은 방식이라 22:00에 시작해 익일 07:00에 끝나는 근무에 익일 02:00 휴게를 넣어도 순서가 그대로 유지됩니다.

## 6. 확장한다면

- 활동 삭제나 시간 줄이기: 지운 시간에 원래 활동을 다시 반영하는 방식으로 구현할 수 있습니다.
- 저장: 변경 전후 리스트를 비교해 수정, 삭제, 추가할 구간을 뽑으면 DB에는 그 차이만 반영할 수 있습니다.
- 마감과 이력: 근무일 마감 여부를 먼저 확인하고, 바뀌는 구간은 변경 전 값을 이력으로 남기는 단계를 저장 앞에 둘 수 있습니다.
